# AI Mock Interview Platform

A full-stack web app for practicing technical and behavioral interviews. Users pick a role, category, and difficulty, get an AI-generated question, write an answer, and receive a score with feedback — similar to how a real interviewer would respond.

## Why I built this

Most "mock interview" tools either give you a static question bank or just let you talk to a chatbot with no structure. I wanted something that mimics an actual interview flow: question first, hints only on request, answer submission, then structured feedback — not everything dumped on screen at once.

---

## What it does

- Register/login with JWT auth
- Pick role (SWE Intern, Data Analyst, Frontend, Backend, Full Stack), category (DSA, Behavioral, HR, System Design), and difficulty
- Get a question generated by Gemini, with hints and an ideal answer hidden behind toggle buttons
- Write an answer and submit it — Gemini evaluates it against the ideal answer and returns a score (1–10), what was good, and what to improve
- Dashboard with real stats: total questions practiced, distinct practice sessions completed, and average score — pulled live from the database
- Platform-wide stats exposed via a public API endpoint for transparency (see above)

## A few things that were harder than expected

**Prisma didn't work on Render's free tier.** I started with Prisma 7 and the new client generator, but kept hitting `MODULE_NOT_FOUND` errors on deploy that didn't happen locally. After a few hours of debugging build logs, I switched the whole backend to raw `pg` queries instead. Less convenient than an ORM, but it deploys reliably and I understand exactly what SQL is running.

**Gemini's free tier rate limits are unpredictable.** Some models would return 503s or quota errors mid-demo. I added a fallback list of models (`gemini-2.5-flash-lite` → `gemini-2.5-flash` → `gemini-3.5-flash`) so if one fails, the backend automatically retries with the next one instead of just erroring out.

**Hosting the backend in India had DNS issues with Railway.** Railway's domains weren't resolving reliably from my network, so I moved the backend to Render. The database also later moved off Railway (free trial expired) to Neon.

**Migrations weren't running on deploy.** My `migrate.js` script created tables using raw `pg` queries, but it was never wired into the start script — so on Render, the app booted with a database that had no tables at all, and any route touching the Session table returned a 500. Fixed by changing the start command to `node migrate.js && node index.js`, which is safe to run on every deploy since the migration uses `CREATE TABLE IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS`.

**"Sessions" and "questions" were the same number.** Every question attempt inserted its own row into `Session`, so a stat meant to represent "how many practice sittings" was really just counting individual questions — attempting 6 questions in one sitting showed 6 sessions. Fixed by generating a `sessionId` (UUID) once per practice page load and attaching it to every question saved during that sitting, then counting `COUNT(DISTINCT sessionId)` for sessions vs. `COUNT(*)` for questions.

## Running it locally

**Backend:**
```bash
cd server
npm install
node migrate.js   # creates User and Session tables
npm run dev
```
You'll need a `.env` file with `DATABASE_URL`, `JWT_SECRET`, `GEMINI_API_KEY`, and `PORT`.

**Frontend:**
```bash
cd client
npm install
npm run dev
```
